Раз бэкенд уже на Go и IPC-протокол бинарный (TLV через Unix socket) — клиент проще всего писать тоже на Go. Никаких лишних зависимостей, протокол уже описан в `tlv.go`, можно переиспользовать типы напрямую или скопировать заголовок.

Альтернативы хуже: Python потребует реализовывать TLV вручную и возиться с `struct.pack`, C/C++ избыточны для тестового CLI, shell-скрипты не потянут бинарный протокол.

---

# Спецификация тестового CLI-клиента

## 1. Назначение

Минимальный интерактивный CLI для ручного тестирования оркестратора в обход Qt-фронтенда. Не production-инструмент.

---

## 2. Технологии

- **Go** — единственная зависимость, `go run ./cmd/cli`.
- Никаких внешних библиотек. Только stdlib + переиспользование пакетов `internal/ipc` из оркестратора (или локальная копия `tlv.go`).

---

## 3. Архитектура

Отдельный бинарь в том же репозитории: `cmd/cli/main.go`.

Структура:

```
cmd/
  cli/
    main.go      — точка входа, REPL
    client.go    — IPC-клиент (connect/send/recv)
    handler.go   — обработка входящих сообщений
```

---

## 4. Запуск

```bash
go run ./cmd/cli [path-to-socket]
```

Если путь не указан — берётся из `$XDG_RUNTIME_DIR/aurora-rag.sock`.

Оркестратор должен быть запущен заранее и ожидать подключения.

---

## 5. Режим работы — интерактивный REPL

После подключения к сокету CLI входит в цикл чтения команд.

```
[aseek]> _
```

### 5.1 Команды

| Команда | Описание |
|---|---|
| `query <текст>` | Отправить RAG-запрос |
| `cancel` | Отменить текущий запрос |
| `ping` | Проверить связь с оркестратором |
| `profiles` | Получить список профилей |
| `switch <name>` | Переключить профиль |
| `help` | Список команд |
| `exit` / `quit` | Завершить работу |

### 5.2 Поведение `query`

- Отправляет `TypeQuery` с payload = UTF-8 строка запроса.
- `RequestID` инкрементируется для каждого нового запроса.
- Токены печатаются в stdout по мере получения (`TypeToken`), без перевода строки между ними.
- По получении `TypeDone` — печатается перевод строки и возврат к промпту.
- По получении `TypeBusy` или `TypeError` — печатается сообщение об ошибке.

### 5.3 Поведение во время активного запроса

Пока идёт стриминг, REPL не принимает новые команды. Единственное исключение — `Ctrl+C` посылает `TypeCancel` и дожидается `TypeDone` или разрыва.

---

## 6. Получение сообщений

Входящие сообщения читаются в отдельной горутине. Канал передаёт их в основной цикл:

```
goroutine readLoop → chan *Message → main loop
```

---

## 7. Вывод

Токены печатаются немедленно при получении — `fmt.Print(token)`, без буферизации.

По завершении (`TypeDone`):
```
\n[done]\n
```

При ошибке (`TypeError`):
```
\n[error] CODE: message\n
```

При `TypeBusy`:
```
[busy] Another request is already in progress
```

---

## 8. Завершение

При `exit` / `quit` / `Ctrl+D`:
1. Если есть активный запрос — послать `TypeCancel`, подождать `TypeDone` (таймаут 3 секунды).
2. Закрыть сокет.
3. Выйти с кодом 0.

При разрыве соединения — напечатать `[disconnected]` и выйти с кодом 1.

---

## 9. Явно не входит в scope

- Цвета, TUI, history команд (readline).
- Сохранение логов.
- Автоматический перезапуск оркестратора.
- Любая бизнес-логика — CLI только транслирует команды в протокол.
