# Search Server API v1.0

Протокол взаимодействия оркестратора с удалёнными поисковыми серверами.

## 1. Транспорт

HTTP/1.1 или HTTP/2. TLS опционально (будущая версия).

## 2. Формат данных

Запрос и ответ — JSON (Content-Type: `application/json`).

## 3. Endpoint

### `POST /api/search`

Основной и единственный endpoint. Сервер сам выполняет embedding запроса и поиск по своей базе.

#### Request

```json
{
  "query": "строка поиска",
  "top_k": 5
}
```

- `query` (string, обязательный) — текст поискового запроса.
- `top_k` (int, опциональный, по умолчанию 5) — количество возвращаемых документов.

#### Response (200)

```json
{
  "results": [
    {
      "index": 0,
      "title": "Заголовок документа",
      "content": "Текст документа...",
      "source": "https://example.com/doc",
      "score": 0.95
    }
  ]
}
```

- `results` (array) — документы, отсортированные по убыванию релевантности.
- `index` (int) — порядковый номер в выдаче.
- `title` (string) — заголовок документа.
- `content` (string) — содержимое документа.
- `source` (string) — источник/URL документа.
- `score` (float, 0.0–1.0) — оценка релевантности.

#### Response (200, пустой результат)

```json
{
  "results": []
}
```

#### Response (4xx/5xx)

```json
{
  "error": "описание ошибки"
}
```

HTTP-статус:
- `400` — невалидный запрос (нет query, пустая строка и т.п.)
- `500` — внутренняя ошибка сервера

## 4. Таймауты

Оркестратор использует таймаут из поля `timeout_ms` профиля сервера.
Если поле не задано — используется `request_timeout_ms` из конфига оркестратора (по умолчанию 15 с).

## 5. Частичный отказ

Если один из серверов профиля недоступен или вернул ошибку:
- ошибка логируется;
- оркестратор продолжает опрашивать оставшиеся серверы.

Если все серверы недоступны — pipeline прерывается, пользователь получает `MsgError`.

## 6. Пример curl

```bash
curl -X POST http://<host>:<port>/api/search \
  -H "Content-Type: application/json" \
  -d '{"query":"пример поиска","top_k":3}'
```
