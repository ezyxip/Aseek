# Спецификация Go-оркестратора (Архитектура v1.0)

## 1. Общая информация

### Назначение

Go-оркестратор является центральным внутренним компонентом приложения семантического поиска с RAG-функциональностью под ОС Аврора.

Оркестратор отвечает за:

* управление жизненным циклом локального `llama-server`;
* IPC-взаимодействие с Qt/QML-фронтендом;
* выполнение RAG-пайплайна;
* сетевое взаимодействие с удаленными поисковыми серверами;
* сборку промптов;
* стриминг ответов локальной модели в UI.

---

## 2. Архитектурная модель

Оркестратор представляет собой отдельную CLI-утилиту, запускаемую фронтендом при старте приложения.

### Основные свойства архитектуры

* Оркестратор жестко привязан к жизненному циклу фронтенда.
* Поддерживается только один IPC-клиент.
* Поддерживается только один активный запрос одновременно.
* Поддерживается только один экземпляр `llama-server`.
* История диалога между запросами не сохраняется.
* Генерация выполняется исключительно локально.
* Семантический поиск выполняется исключительно удаленно.
* При завершении фронтенда оркестратор завершает работу автоматически.

---

# 3. Жизненный цикл компонентов

## 3.1 Запуск приложения

При старте Qt-приложение:

1. запускает процесс оркестратора;
2. ожидает готовности IPC-сокета;
3. подключается к IPC-серверу оркестратора.

---

## 3.2 Запуск llama-server

После старта оркестратор обязан автоматически запускать локальный `llama-server`.

Причина:

* модель загружается в память длительное время;
* warm-up должен происходить заранее.

---

## 3.3 Завершение приложения

При отключении IPC-клиента (Qt):

1. оркестратор отменяет активный запрос;
2. завершает `llama-server`;
3. удаляет IPC socket file;
4. завершает собственный процесс.

---

# 4. Внутренняя архитектура оркестратора

Оркестратор состоит из следующих внутренних модулей:

| Модуль             | Назначение                                   |
| ------------------ | -------------------------------------------- |
| IPC Server         | Работа с Unix Domain Socket и TLV-протоколом |
| Request Manager    | Управление активным запросом                 |
| Process Supervisor | Управление `llama-server`                    |
| Search Pipeline    | Выполнение embedding/search                  |
| Prompt Builder     | Формирование RAG-промптов                    |
| Profile Manager    | Работа с профилями                           |
| Config Manager     | Загрузка runtime-конфигурации                |
| Streaming Engine   | Передача токенов в UI                        |
| Logger             | Structured logging                           |

---

# 5. Runtime-конфигурация

## 5.1 Формат хранения

Оркестратор должен использовать внешний JSON-конфиг.

Пример пути:

```text
~/.config/aurora-rag/orchestrator.json
```

---

## 5.2 Назначение

Конфигурация должна позволять изменять runtime-параметры без перекомпиляции оркестратора.

---

## 5.3 Пример конфигурации

```json
{
  "llama": {
    "binary": "/opt/aurora/bin/llama-server",
    "model": "/opt/aurora/models/vikhr-qwen-q4.gguf",
    "port": 8081,
    "ctx_size": 4096,
    "threads": 4,
    "slots": 1,
    "batch": 256,
    "gpu_layers": 0
  },

  "streaming": {
    "flush_interval_ms": 40
  },

  "network": {
    "request_timeout_ms": 15000
  },

  "logging": {
    "level": "debug"
  }
}
```

---

# 6. IPC-сервер

## 6.1 Транспорт

Для IPC используется Unix Domain Socket.

---

## 6.2 Путь сокета

Оркестратор обязан использовать защищенный runtime-path:

```text
$XDG_RUNTIME_DIR/aurora-rag.sock
```

Использование `/tmp` запрещено.

---

## 6.3 Ограничения

* Поддерживается только один клиент.
* При подключении второго клиента соединение должно отклоняться.

---

# 7. Формат IPC-протокола

## 7.1 Заголовок пакета

Все IPC-пакеты используют бинарный заголовок фиксированной длины.

### Размер заголовка

```text
16 байт
```

---

## 7.2 Формат заголовка

| Поле      | Размер  | Тип    |
| --------- | ------- | ------ |
| Magic     | 2 байта | uint16 |
| Version   | 2 байта | uint16 |
| Type      | 4 байта | uint32 |
| Length    | 4 байта | uint32 |
| RequestID | 4 байта | uint32 |

---

## 7.3 Порядок байт

Все числовые значения передаются в формате Big-Endian.

---

## 7.4 Magic

Фиксированное значение:

```text
0x4152
```

---

## 7.5 Version

Текущая версия протокола:

```text
1
```

---

# 8. Модель обработки запросов

## 8.1 Ограничения

Поддерживается только один активный запрос одновременно.

---

## 8.2 Поведение при новом запросе

Если активный запрос уже выполняется:

Оркестратор возвращает:

```json
{
  "code":"BUSY",
  "message":"Another request is already in progress"
}
```

---

# 9. Выполнение RAG-пайплайна

## 9.1 Общий pipeline

```text
Query
  ↓
Embedding
  ↓
TopK Search
  ↓
Reranking
  ↓
Prompt Build
  ↓
llama-server
  ↓
Streaming
```

---

## 9.2 Cancellation model

Каждый запрос должен выполняться внутри собственного `context.Context`.

При отмене:

* останавливаются HTTP-запросы;
* прерывается генерация;
* завершается streaming;
* освобождаются внутренние ресурсы.

---

# 10. Управление llama-server

## 10.1 Supervisor model

Оркестратор обязан запускать `llama-server` как дочерний процесс.

---

## 10.2 State machine

```text
STOPPED
  ↓
STARTING
  ↓
READY
  ↓
FAILED
  ↓
RESTARTING
```

---

## 10.3 Проверка готовности

После запуска оркестратор обязан выполнять HTTP health-check `llama-server`.

До получения статуса READY обработка пользовательских запросов запрещена.

---

## 10.4 Политика рестартов

При аварийном завершении `llama-server`:

* выполняется до 3 попыток перезапуска;
* используется exponential backoff.

### Последовательность задержек

```text
1s → 2s → 5s
```

---

## 10.5 Fatal failure

Если после 3 попыток `llama-server` не удалось восстановить:

1. Qt получает `MsgError`;
2. оркестратор завершает работу.

---

# 11. Работа с llama-server API

## 11.1 Транспорт

Взаимодействие осуществляется через HTTP API.

---

## 11.2 Формат API

Используется OpenAI-compatible API.

---

## 11.3 Endpoint

Используется endpoint:

```text
/v1/chat/completions
```

---

## 11.4 Streaming

Генерация всегда выполняется с:

```json
"stream": true
```

---

# 12. Slot Context Caching

## 12.1 Назначение

`slot context caching` используется для:

* кэширования системного промпта;
* повторного использования RAG-шаблонов;
* ускорения обработки похожих документов.

---

## 12.2 Ограничения

Поддерживается только один слот.

---

# 13. Prompt Builder

## 13.1 Ответственность

Формирование всех промптов выполняется исключительно Go-оркестратором.

---

## 13.2 Хранение шаблонов

Prompt templates должны храниться во внешних файлах.

Пример:

```text
~/.config/aurora-rag/prompts/
```

---

## 13.3 Рекомендуемые шаблоны

```text
system.txt
rag.txt
no_results.txt
```

---

## 13.4 Формат RAG prompt

Рекомендуемый минималистичный формат:

```text
Ты отвечаешь только по предоставленным документам.

Документы:

[1]
...
[/1]

[2]
...
[/2]

Вопрос:
...

Ответ:
```

---

# 14. Streaming model

## 14.1 MsgModelToken

Payload содержит:

* raw UTF-8 text;
* без JSON-обертки.

---

## 14.2 Ограничения

Payload обязан содержать только корректный UTF-8.

---

## 14.3 Batching

Оркестратор должен поддерживать batching токенов.

Рекомендуемый flush interval:

```text
30–50 ms
```

---

# 15. Профили серверов

## 15.1 Хранение

Профили хранятся локально в JSON-файле.

Пример:

```text
~/.config/aurora-rag/profiles.json
```

---

## 15.2 Содержимое профиля

На текущем этапе профиль содержит только список search-серверов.

---

## 15.3 Будущая совместимость

Архитектура должна предусматривать возможность добавления:

* auth headers;
* bearer tokens;
* TLS configuration;
* API keys.

---

# 16. Network policy

## 16.1 Поведение при частичном отказе

Если часть search-серверов недоступна:

* ошибка логируется;
* работа продолжается.

---

## 16.2 Полный отказ

Если недоступны все search-серверы:

* pipeline прерывается;
* пользователь получает `MsgError`.

---

# 17. Logging

## 17.1 Формат

Используется structured logging.

Рекомендуемый формат:

```json
{"ts":"...","level":"INFO","module":"ipc","msg":"client connected"}
```

---

## 17.2 Log domains

Минимально поддерживаются:

* ipc
* pipeline
* network
* llama
* supervisor
* profiles

---

## 17.3 Privacy

В release-сборках запрещается логировать:

* пользовательские запросы;
* документы;
* полные промпты.

---

# 18. Error handling

## 18.1 Все ошибки должны:

* логироваться;
* возвращаться через `MsgError`;
* быть привязаны к конкретному `RequestID`.

---

## 18.2 Формат ошибки

```json
{
  "code":"ERROR_CODE",
  "message":"Human readable description"
}
```

---

# 19. Ограничения MVP

На текущем этапе не поддерживаются:

* многопользовательский режим;
* сохранение истории;
* многосессионность;
* параллельная генерация;
* hot-reload моделей;
* несколько llama-server;
* offline-режим;
* локальный embedding;
* telemetry/metrics subsystem.
